# CI-TRACE V7 — Evidence-bearing Artifact Trust Boundary Research
Research date: 2026-10-11. Status: experimental; separate draft PR #4.

## Decision and rationale
V3–V6 were dominated by direct downloaded-file execution and by labels generated from their own rule semantics. The core limitation was **incorrect problem abstraction**, not insufficient regex coverage. Two independent September 2026 GitHub Security Lab disclosures demonstrated different sinks:

1. **GHSL-2026-204 / spiffe/spire:** artifact content can replace a checked-out trusted JavaScript helper under the checkout workspace, then `actions/github-script` imports the replaced module with issues/pull-requests write permissions. No `bash ./artifact.sh` step is needed.
2. **GHSL-2026-225 / actions/attest:** artifact-supplied `head-ref` passes through `$GITHUB_OUTPUT` into privileged `actions/checkout.ref` and `git push` for a target branch. This is not necessarily direct code execution.

Original advisories:
- https://securitylab.github.com/advisories/GHSL-2026-204_spiffe_spire_repository/
- https://securitylab.github.com/advisories/GHSL-2026-225_actions_attest/

**The attack classes were already disclosed by others.** V7's research claim is a bounded and explainable integration of both trust-path patterns, not first discovery of those vulnerabilities or proof of a fundamentally new analysis algorithm.

## Technical design

Two deliberately bounded rules produce machine-readable *evidence atoms*:

- `ARTIFACT_OVERLAY_IMPORT`: untrusted producer event + matching `workflow_run` + explicit triggering-run Artifact download + trusted code checkout before download + compatible extraction destination + subsequent module import.
- `ARTIFACT_METADATA_REF_WRITE`: cross-run Artifact download + artifact metadata read `head-ref` + output-channel binding + later branch selection via `checkout.ref` or `git push` + declared write permission, without a recognized restrictive origin guard.

Retain V3–V6 as comparator modules. V7 is read-only and never executes user-supplied workflows.

- https://github.com/junlin20011207/ci-trace-sandbox/actions/runs/38137847258 — 118 tests passed, same historical samples: **V6 matched 2/4 known states; V7 matched 4/4**.
- The two historically vulnerable samples are each detected by V7 in their respective targeted category; their later fixed-control snapshots are not detected for that category.
- One previous V7 hosted run https://github.com/junlin20011207/ci-trace-sandbox/actions/runs/38137702164 passed 115 tests; three later provenance-gate regression tests were added.
- The local independently implemented proof-of-concept replay passed **26** sandbox tests; it used an inert JavaScript module whose return value changed from `TRUSTED` to `OVERLAID` after simulated artifact extraction. With extraction isolated, the marker stayed `TRUSTED`. This is a harmless filesystem/control-flow demonstration, **not a real GitHub cross-run exploitation attempt**.

## Experiments and falsification cycles

1. Route A: more execution regex patterns (V3–V6). Hard ceiling when sensitive sinks are module import and metadata-controlled `git push`.
2. Route B: workspace overlay graph. Positive on GHSL-2026-204 historical workflow and negative on isolated download fixed workflow.
3. Route C: metadata channel tracing. Positive on GHSL-2026-225 historical workflow and negative on origin-bound fixed workflow.
4. Mutations: mismatch artifact name, mismatched run-id, reversed checkout/download, disabled import, unrelated sparse checkout, and isolated download are negative controls. An `OR always()` bypass of a textual origin guard produced a false exclusion during development; the guard check and three regression tests were corrected.
5. Real CI reruns are the source of record. No prior failed run was reclassified as a pass.

```bash
python -m pip install -r requirements.txt pytest
python -m pytest -q
python -m benchmarks.public_cases_v7 --assert-results
python -m ci_trace.scanner_v7 .github/workflows
```

Historical snapshots are stored as inert .yml files under `research_corpus/` — **never** copied to `.github/workflows/` for automatic execution.

## Limitations and proof obligations

- Evidence of a structural path is **not** evidence that an attacker actually controls specific extracted bytes or that code executes in the target permission context.
- Archive entry normalization, symlinks, partial checkout cleanup, aliases, dynamic module names, other languages, expression transformations and cross-job propagation remain incomplete.
- The `$GITHUB_OUTPUT` tracking recognizes only a specifically named head-ref channel, not a general taint-analysis intermediate representation.
- The origin guard classifier is a narrow string-based heuristic, even after the OR correction. It is not a sound GitHub Actions expression solver.
- The corpus has only 2 independent positive incidents. It is too small and retrospectively selected to establish a real-world precision/recall estimate or high competitive standing.
- Poutine same-corpus testing and independently adjudicated, blind-labeled examples are still needed.
- Recent 2026 GitHub checkout protections address certain fork PR checkouts, not all artifact-overwrite or metadata problems: https://github.blog/changelog/2026-06-18-safer-pull_request_target-defaults-for-github-actions-checkout/

## Selected next hypothesis
Build a source-to-sink intermediate representation with file system provenance, Artifact member paths, expression ASTs, binding constraints, and authorization boundary predicates, then compare on a larger corpus containing both real fixed/unfixed pairs and unknown cases. This must be measured prospectively, with a frozen evaluation set and failure analysis. The current V7 code is a **working research baseline** for that system, not the completed proof engine.
