# CI-TRACE V8 — Research pivot from static warnings to enforced artifact trust boundary
Research snapshot: 2026-10-11. Scope: authorized defensive CI/CD supply-chain security.

## 1. Root cause and research hypotheses

The V3–V6 approach identified explicit download-to-execution patterns; the later V7 approach modeled two externally disclosed artifact overwrite / metadata-to-ref-write trust paths. This work was useful but limited:
- Labels for most tests were generated by authors from the same rule assumptions.
- Retrospective evidence amounted to two independently reported GHSL incidents plus their fixed snapshots: V6 2/4, V7 4/4 expected historical/control matches. This does not yield real-world precision or recall.
- Zizmor and Poutine analyze overlapping but different issue families; comparing raw counts is not an efficacy metric.
- Even a correct static alert did not stop a privileged consumer from extracting or using untrusted artifact data.

**New hypothesis:** a runtime gate that derives provenance from authenticated GitHub Actions API objects, validates a trusted policy and the archive digest, and releases only inert data into an isolated location can demonstrably prevent several specific artifact-to-sensitive-sink paths in a controlled setting, without needing to infer general exploitability from a YAML heuristic.

## 2. Design and change in technical direction

### V7 (preserved): discovery and explanation
- Source–sink evidence for workspace module overlay (`ARTIFACT_OVERLAY_IMPORT`).
- Artifact metadata to privileged ref-write channel (`ARTIFACT_METADATA_REF_WRITE`).
- Each is bounded; neither is a universal taint solver.

### V8 (new): enforcement
`ci_trace/provenance_guard.py` provides:
1. Explicit expected source run ID, source event, repository, commit SHA, artifact identity and status policy.
2. SHA-256 verification of actual downloaded ZIP bytes against the `digest` supplied by GitHub's Artifact REST API.
3. Per-entry ZIP policy: traversal/absolute/Windows drive rejection, case-fold collisions, symlinks and special file rejection, extension allowlist, entry count, total extracted bytes, compression ratio and archive size limits.
4. Private extraction into a newly created directory **outside** the checkout workspace, cleanup of partially extracted data on denial.
5. The only approved branch identity exposed in a result originates from the authenticated run event, not an `head-ref` file carried by the artifact.

`ci_trace/github_api_gate.py` fixes a trust assumption in the initial prototype: instead of accepting arbitrary source JSON, it queries fixed-host HTTPS `api.github.com` run and artifact endpoints using a token in the environment, and cross-checks run ID, artifact ID, source SHA, repository and repository ID before delegating to the fail-closed gate.

The artifact is still downloaded separately. The consumer must run trusted code, retrieve the ZIP from the correct authenticated endpoint, enforce all decisions and not use artifact metadata as an independent authority.

## 4. Reproduce

```bash
python -m pip install -r requirements.txt pytest
python -m pytest -q
python -m benchmarks.public_cases_v7 --assert-results
python -m benchmarks.provenance_gate
python -m benchmarks.fuzz_gate
```

To use the auth-fetched gate with *trusted repository policy* and an archived ZIP:
```bash
export GH_TOKEN=... # Actions: read, never place in artifacts/logs
python -m ci_trace.github_api_gate \
  --repository OWNER/REPO --run-id RUN_ID --artifact-id ARTIFACT_ID \
  --archive artifact.zip --policy policy.json \
  --output-root TRUSTED_TEMP_LOCATION --workspace TRUSTED_GITHUB_WORKSPACE
```

The GitHub Actions proof-of-function is in `.github/workflows/v8-real-artifact-probe.yml`, read-only, and does not run untrusted code. Archive source Run ID and ZIP name are fixed for historical reproducibility.

## 5. Scientific claims we do NOT make

- Two public GHSL cases are third-party discoveries. V8 does not claim those attack classes as its original discoveries.
- Unit success, 500 seeded scenarios or a true ZIP digest are NOT proof of high real-world vulnerability recall, zero false positives, or perfect protection against unknown exploit paths.
- V8 does NOT prove safety of arbitrary artifact content. It blocks unsafe formats and releases data in a separate namespace; a consumer can undo this benefit by unsafely copying or executing files.
- No privileged cross-run exploitation or malicious third-party code was executed. The live test consumed a benign archived ZIP from an earlier completed workflow.
- The solution is a **composition of standard security controls and a specific static finding model**, not an independently established new cryptographic primitive or formally verified analysis system.
- Attacker influence on the policy file, GitHub token, checkout, API transport, underlying runner host, or post-approval sinks is outside the prototype threat model. Deployment must use trusted code from the default branch.
- SHA-256 anchored to GitHub's authenticated API provides platform-level integrity relative to that API; it does NOT imply the producer is trustworthy.
- This version has a restrictive `allow_extensions` rule and compression thresholds, so legitimate artifacts may be rejected. Generality and cost in larger repositories remain unmeasured.
- The Poutine baseline on identical target scenarios and independently reviewed, forward-looking live workflows are still outstanding.

## 6. Competition readiness

The current competition guidance emphasizes defensive, original, independently developed and practical security works. V8 advances the project from an alert-only checker to a demonstrable prevention component with real cloud-platform metadata validation.

**Preferred submission direction:** CI-TRACE *Evidence-to-Enforcement* — cross-workflow artifact provenance and least-authority isolation, integrating explainable V7 trust-path discovery with a V8 deployable runtime gate.

However, the strongest outstanding proof obligation is a **larger frozen blind evaluation set** and a truly end-to-end *unprivileged* cross-workflow replay on a dedicated default-branch test repository. The high-level award outcome cannot be inferred from current evidence.

## 7. Next falsification protocol

1. Independently label at least 20 genuine cross-workflow artifact producers and consumer workflows from unrelated repositories, including legitimate benign pipelines, unknown cases, and previously disclosed vulnerabilities. Freeze versions and labels before tuning.
2. Verify missing modalities: composite actions, Python imports, symbolic links and dynamic shell expressions; record abstentions rather than calling them safe.
3. Run zizmor and Poutine on the **same pinned snapshots**; map relevant alerts to a shared question while preserving tool-specific taxonomies.
4. Move both producer and consumer into an owned, unprivileged default-branch test repository with no secrets; demonstrate a real completed `workflow_run` context and authenticated artifact retrieval across runs.
5. Benchmark startup, API latency, archive size throughput, false denials, fault injection and policy adoption overhead.
