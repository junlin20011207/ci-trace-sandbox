# CI-TRACE 第22轮：完整系统集成、强基线、正式模型验证与真实云端可信交接

日期：2026-10-12 · 研究样机 · 不具备生产审批权限

## 执行摘要

本轮把此前21轮协议研究整合为一套可操作的软件原型，并完成原先未执行的四类重要任务：完整产品、配对基线、真实 TLA+ 验证、独立数据处理。额外完成 GitHub Sigstore 签发、双托管运行器来源核验和恶意篡改拒绝。所有可完成的零密钥研究部分均由当前沙箱及 GitHub连接工具完成，没有要求使用个人电脑。

### 完成的实际交付

1. **可运行产品**：FastAPI + 静态控制台 + 临时 Ed25519 + 在线 SQLite 发行者 + 本地真实裸 Git 仓库。九种发布/攻击场景均通过自己的明确断言；`tests/test_product.py`4项产品/攻击/API 回归通过。
2. **复用既有协议**：第21轮30项真实Git与数据库协议单测通过，7项不同Linux UID的真实进程/文件隔离回归通过；保持原有6项缺陷修复。
3. **配对强基线**：研究者实现 A 代码审查代理，B 外部审批 + 内容/目标绑定 + 时效/撤销 + 一次性 SQLite占用，C 完整 CI-TRACE。九种作者设计场景使用相同输入。B 仍存在检查后普通 Git push 的竞态，实际Git重复演示；C 拒绝更新他人已创建引用。发布后崩溃，B保守暂停，C只读验证已成功的提交。**不是产品商家综合评测，不是第三方真实事件。**
4. **性能**：9个场景各测10次本地完整时延，记录原始数组（详见`results/latency.json`）。正常发布P50约59.21ms、P95约71.86ms；崩溃并恢复P50约594.01ms、P95约650.62ms，包含模拟子进程启动、Git、SQLite，不包括跨平台网络。
5. **公平计时补充**：为避免只测C协议内部计时、却把B的仓库初始化时间算进去，另加入B/C各10次的完整场景墙钟配对测量：合法发布B P50=76.46ms，C P50=102.64ms，增加约26.18ms（同一沙箱，不含网络）；崩溃处理B=89.22ms只保守暂停，C=649.87ms真正恢复确认（不等价的处理目标，不能据此直接评价吞吐）。原始数组见`results/baseline_b_latency.json`。
6. **形式化**：独立Python BFS检查36可达状态、67次转换；故意弱化模型得到 `reserve → check absence → other creates ref → ordinary push` 反例。真实 GitHub托管 TLC v1.7.4 完整遍历36个不同状态、68个生成状态，无违反所定义不变量的反例。模型中不存在任意网络分区或恶意Git管理员；其结论不扩展到真实所有运行。
7. **独立数据**：从 `sparkrew/github-actions-security` 固定提交 `327c162...` 读取真实元数据：2722份工作流元数据，121个仓库条目，448条人工弱点标签、50份不同被标注工作流；来源研究README提到54份选取样本。弱点类别计数 `UDW:330, EPW:35, HGW:29, GRCW:18, IW:14, KVCW:8, AIW:7, SEW:4, PTW:3`。这些是安全弱点正标签而非发布批准真值，不能据此计算业务 FPR/FNR。
8. **真实第三方审批事件**：GitHub Actions 实际检索公开第三方合并PR：Flask 2、Node.js 12、Rust 12；见 `results/public_pr_review_observation.json` 及正式云端日志。实际审查事件只是代码审批，不是 CI-TRACE 的独立业务批准。
9. **真实签名与双机器交接**：GitHub托管运行器通过官方 `actions/attest@v4` 获取Sigstore短期证书签名并关联公开透明日志。另一台独立托管运行器通过GitHub artifact下载文件，检查证书工作流精确身份、对应的source digest与ref，再修改文件一个字节验证拒绝。GitHub产物证明不是外部企业批准书，亦不构成双向mTLS业务RPC。

## 配对对照：数字说明什么，不说明什么

以9个研究者构造的业务/故障场景为单位：

| 指标 | A 简单审批代理 | B 增强外部审批代理 | C CI-TRACE |
|---|---:|---:|---:|
| 5个无权发布场景中出现未授权副作用的场景数 | 5 | 1 | 0 |
| 4个研究者定义的合法/恢复场景中达到目标流程状态的场景数（含并发仅预留成功） | 1 | 2 | 4 |
| 崩溃后自动确认远端已完成的发布 | 否 | 否（保守暂停） | 是（只读验证） |
| 对目标引用抢先创建的竞态防护 | 无 | TOCTOU存在 | Git原子创建约束 |

**方法界限**：B是自行编写的“合理但缺少原子引用约束和可信恢复”的强基线，不是 GitHub 官方完整功能。若为 B 增加与 C 相同的 Git CAS 和恢复协议，其结果可能与 C 相同；目前不能宣称 CI-TRACE 必然优于成熟平台的最佳集成。安全收益是在公开、可复现的实现假设下成立。

## 距离“正式竞赛获奖级”的剩余验收条件

### 可自主完成并已完成（当前会话）
- 完整可运行Web和CLI演示原型。
- 真实Git、并发、故障恢复和结构化对照试验。
- TLA+真实TLC验证而非只提供文字规范。
- 公开第三方工作流及PR审核数据的聚合、固定版本、许可风险说明。
- Sigstore真实发行与另一台机器验证及篡改负例。

### 不能由当前研究人员单方面“做成真实外部授权”的项目
- 第三方机构对具体发布拥有真实批准/拒绝权，以及独立持有无法被项目作者替换的权威私钥、信任根。
- Gitee 生产目标的受保护发布凭据、可写入权限及管理员配置。暴露过的旧令牌不能使用。
- GitHub/Gitee生产级跨平台、强制审批和真实双机mTLS发行服务端到端验收。
- 跨企业真实业务事件的独立标签与同等真实审批预算的生产对照；目前只是独立公开元数据与研究者构造场景。

## 原创性谨慎表述

密码算法、TUF过期/密钥控制、Git create-only/CAS、GitHub部署环境、Sigstore SLSA、外部审批本身均已有成熟先例。合理的候选研究贡献是**操作级授权与实际Git引用一致性、单次预留线性化、故障后只读结果证明三者的组合及可验证失败关闭**。是否明显领先同功能完备的外部审批+CAS+恢复系统，仍需更严谨的开放实现对照，而不是仅凭测试数量证明原创。
